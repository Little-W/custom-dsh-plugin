# UI 界面风格设计

先查看要修改的真实页面、相邻页面和已有组件、主题变量、图标、字号与间距约定。保持用户指定的产品方向；已有设计系统时，优先用其组件和 tokens 表达新设计。新界面缺少方向时，可用一段简短说明确定用户任务、内容密度和视觉重点，随后实现可查看的方案，不需要为了常规样式取舍反复询问。

## 让风格服务于内容

把风格落实为可复用的决策：页面背景与内容层、正文与次要文字、主操作与普通操作、标题与列表行、图标尺寸及基线、边框与选中状态。优先复用已有字号和间距阶梯；新增值应有明确用途。同一级操作组和摘要组使用同一级文字样式，图标和文字以同一个布局容器对齐。长标题、中文、西文路径和数字都要用真实内容检验。

根据界面任务选择布局：工作台需要可扫描的信息密度，移动操作页需要清晰的动作顺序；不要把所有内容统一塞进同样大小的卡片。颜色、阴影和圆角应强化层次，不靠堆叠渐变或装饰掩盖结构。用户要求风格方案时，提出少量有实际差别的方向，例如密度、导航结构、排版或色彩层级，并将选定方向贯彻到页面状态中。

移动端先决定信息如何重排：哪些操作合并、哪些内容滚动、导航如何收起、长内容如何换行。工具栏在常规与多选状态切换时应保留稳定的标题和操作区域，窄屏时整组重排，避免按钮散落到无关行。触控区域可以大于可见图标；不要靠缩小所有字号来容纳桌面布局。验证横屏、长内容、空状态、加载、错误和禁用状态；固定底栏和弹层需要检查实际可视区域与遮挡。

## 在真实页面中验证

DSH 插件使用 `plugin_preview`，传入已构建的插件目录；有组件依赖时一起传入 `plugin_paths`。先确认产物版本和 `sourceChanged=false`。

- 手机页面必须显式选择 `mode:"mobile"`。工具先在空白 Chrome 标签页设置移动 UA、触控、移动视口和 DPR，再加载 DSH；核对 `browser.verified=true`、`emulationAppliedByTool=true` 与返回的实际状态。DSH 会缓存首次手机设备检测，宽度小不代表手机行为已生效。桌面行为对照使用 `mode:"desktop"`。
- 继续使用当前 Chrome DevTools 工具在返回的 `browser.pageId` 上检查和操作真实界面；调用 `capture` 可把当前真实画面更新到插件面板。Chrome 不可用或权限拒绝时，不能把 `mode:"layout"`、设备框或普通浏览器页面当作已启用手机模式。
- `devicePreviewUrl` 是仅布局的 CSS 视口设备框，可切换设备和旋转；它不设置 UA、DPR 或触控。手动使用 Chrome 时，先配置完整移动仿真和 UA，再首次加载页面；对已加载的 DSH 切换模式后必须重载，避免设备检测缓存。
- 修改或构建后调用 `reload`，新实例会按所选模式重新配置 Chrome；旧截图和旧标签页不能证明新版界面有效。

检查主要用户动作和页面状态，并用 DOM 几何数据定位文字/图标重叠、行高、对齐、溢出或遮挡；再用截图判断整体层级与视觉平衡。仅改变 viewport 不会自动打开目标导航或构造测试状态，应通过真实控件进入相应页面。

Chrome 和设备框检查的是网页渲染，不能证明原生 Android/Compose、系统键盘、安全区或真实设备行为；原生界面需要项目现有设备/模拟器验证路径。工具暂不可用时，继续可完成的实现，并标明尚未验证的部分。

交付说明保持简短：实际修改的文件、采用的风格决策、已检查的页面与尺寸、截图/交互证据、仍未覆盖的情况。语法检查、启动成功、手工拼装的示意页面，都不能代替对修改后真实页面的观察。
